# 0007 システムメールの送信主体を `no-reply@` 実ユーザーにし、ドメイン全体の委任を OAuth 同意に置き換える

- 状態: 実施済み（2026-09-29 CEO 承認「最適を選択する」。Workspace 1 席、月額 約 ¥800。2026-09-30 本番切替、実送信で確認）
- 決定者: ロウ（CEO）／起案: IV

## 文脈
- 控えを CEO 自身のアカウントから自分宛て（contact@ はエイリアス）に送ると、Gmail は「自分から自分へ」として受信トレイに出さない（2026-09-29 実測: 「すべてのメール」にのみ存在）
- ドメイン全体の委任は、鍵が漏れるとドメインの全ユーザー（CEO 含む）になりすませる過大権限
- 最先端企業はシステムのメールを人のアカウントから出さない（送信主体の分離）

## 選択肢
1. 送信専用ユーザー `no-reply@reyz.inc` を作り、そのユーザー本人の OAuth 同意（scope: 送信のみ）で送る。委任と SA 鍵を廃止
2. Gmail のフィルタで見えるようにする（自己宛て配送への適用は未確認、権限は過大のまま）
3. Gmail API の挿入（gmail.insert）で受信トレイに置く（鍵漏えい時に偽メールを受信トレイへ差し込める権限になる）

## 決定
1。帰結として、鍵が漏れた場合の影響は「no-reply の送信」に限定され、控えは別アカウントからの通常配送として受信トレイに入る。no-reply の「送信済み」がシステムメールの完全な保管庫になる。

## 帰結
- OAuth 同意画面を「内部（Workspace のユーザーのみ）」にするため、GCP プロジェクトは reyz.inc の組織配下に置く（個人 Gmail 配下の旧プロジェクトは PoC 用途に限定）。内部アプリは Google の審査不要で、リフレッシュトークンは失効しない（外部アプリのテスト状態は 7 日で失効）
- 秘密は OAuth クライアント ID／シークレット／リフレッシュトークンの 3 つに置き換わる。リフレッシュトークンは no-reply のパスワード変更・6 か月未使用・取り消しで失効する（監視: `contact-watch` と `stack-e2e` の pass ケースが検知）
- ストリーム分離（専用サブドメイン `mail.reyz.inc`）は発動条件つき（顧客サイトの送信代行開始）で、この決定の adapter 構成で作り直しなく追加できる
- 実施で分かったこと（2026-09-30）: (1) 送信専用ユーザーは作成直後に初回ログインと 2 段階認証の登録を済ませないと、組織ポリシーで同意のログインが拒否される (2) 同意は必ず本人の口座で行い、同意画面の口座名を確認する。個人の口座で同意すると Gmail が差出人を本人のアドレスへ書き換える（[事故記録](../incidents/2026-09-30-oauth-consent-wrong-account.md）) (3) 移行期間用に残していたサービスアカウント経路は 2026-09-30 に削除し、adapter は OAuth のみ。同意の自動化は ADR-0008 で扱う
