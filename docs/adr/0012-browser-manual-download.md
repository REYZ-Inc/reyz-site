# ADR-0012: 配信マニュアルをブラウザ内でカスタマイズして保存する

## 文脈

2026-11-16のユーザー指示により、REYZ Inc.サイトから、名称と配色を選んだ42ページの配信マニュアルをPDFで保存できる機能が必要になった。現在のサイトはGitHub PagesとCloudflareで配信する静的サイトである。名称・配色だけの変更に、新しい入力データ保管先や常時稼働するPDF生成サーバーを追加する必要はない。

## 選択肢

1. 全テーマのPDFを作り分け、ブラウザで名称だけを追加する。構造は簡単だが、原稿が重複し、配布・更新するファイル数が増える。
2. サーバーで毎回PDFを生成する。入力名称の送信、API運用、費用と失敗経路が増える。
3. 単一テンプレート、限定された配色トークン、名称配置データからブラウザで生成する。

## 決定

3を採用する。元PDFを管理されたビルド処理でテンプレート化し、自由入力はpdf-libの文字描画APIにのみ渡す。文書構造・本文・画像・内部リンクは元のPDFを維持する。ライブラリとフォントは固定したものを自社サイトから遅延配信する。必要なカスタム字形はfontkit経由で埋め込む。実装の確定条件は名称・配色・全ページの回帰とスマホ幅の実測であり、確認前の推測を完了として扱わない。

サイト内の主導線はCreatorのTikTok LIVE説明直後、補助導線は共通フッター、操作ページは `/manual` とする。既存の主ナビと固定文言は保持する。

## 帰結

- 名称は端末内に留まり、新しい秘密情報・バックエンド・認証設定は不要。
- どの色も同一の原稿を使うため、内容更新の重複を避けられる。
- 生成時の帯域とメモリ、フォント対応範囲、iOSの保存挙動を検証対象にする。
- 非同期生成の後はブラウザのユーザー操作権限が失われる可能性があるため、生成後に新たなタップで保存・共有する経路を残す。
- 本番反映は既存の保護ルールとPR/CI/Pages配備を通す。
