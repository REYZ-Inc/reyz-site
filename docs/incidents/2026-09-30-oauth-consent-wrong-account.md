## 根本原因
1. 手順が「同意する口座」を確認する段を持たず、ブラウザのログイン状態に依存していた（口座選択画面が出るとは限らない）
2. 同意で得たトークンが誰のものかを、配備前の関門（`stack-e2e`）が検証していなかった（トークン取得の成否しか見ない）
3. 送信専用ユーザーの初回ログインと 2 段階認証の登録が手順に無く、同意の途中で組織ポリシーに阻まれた

## 是正（実施済み）
- シークレット ウィンドウで no-reply@ 本人としてログインし直し、同意画面の口座名を確認してから許可 → Secret 更新 → 再配備 → 実送信で差出人と受信トレイを確認
- 手順書（`workers/contact/README.md` 設定手順）に「初回ログイン＋2SV 登録」「シークレット ウィンドウ」「同意画面の口座名の確認」「実送信で差出人を確認」を追加
- `contact-logs` の一覧に認証方式 `auth` を表示（PR #18）

## 再発防止
- 同意の自動化（ADR-0008 予定）: workflow が同意リンクを `login_hint=no-reply@reyz.inc` 付きで生成し、コード交換後に ID トークンの `email` が送信専用ユーザーと一致しなければ **保存せず失敗**する。人の判断に頼らない
- 上流の順序を固定: ユーザー作成 → 初回ログインと 2SV 登録 → 同意（手順書に反映済み）
- 残作業（ロウ）: horiuchi@ に付いた「REYZ Mail Sender」のアクセス権を削除（誤同意のトークンを失効させる）

## 教訓
- 「トークンが取れた」は「正しい口座のトークンが取れた」ではない。検証は結果（差出人）で行う
- 受信トレイに入らない理由を推定で片付けない。Gmail の仕様は「自分から自分の別名宛て」であり、差出人が誰かを先に確定させるべきだった
